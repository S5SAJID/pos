* **The Issue:** 
  ```typescript
  throw new Error("Invalid SQL syntax. " + err.message || "Invalid SQL syntax.");
  ```
  Because `+` has higher operator precedence than `||`, `"Invalid SQL syntax. " + err.message` evaluates first. If `err.message` is `undefined`, the result is `"Invalid SQL syntax. undefined"`, which is truthy, making the `||` fallback dead code.
* **Recommendation:**
  * Fix the precedence: `new Error(`Invalid SQL syntax: ${err.message ?? "Unknown error"}`)`.

## 💡 TECHNICAL ARCHITECT DEBT & NOTES

1. **Database Least Privilege vs. Application-Level WAF:**
   * Validating raw SQL using an AST parser while connecting to Neon as a privileged database owner is a fragile architecture. Even minor differences between `node-sql-parser` and PostgreSQL's native parser (such as dollar quotes `$$`, type casts `::`, CTEs, or window functions) will result in either false-positive query rejections or security bypasses.
   * **Target Architecture:** Configure a dedicated read-only Postgres user/role for the MCP integration:
     ```sql
     CREATE ROLE mcp_readonly WITH LOGIN PASSWORD '...';
     GRANT SELECT ON products, inventory, expenses, transactions, transaction_items TO mcp_readonly;
     REVOKE ALL ON account, session, users, verification FROM mcp_readonly;
     ```
     By enforcing access control at the database engine level, an attacker cannot read sensitive tables or perform mutations even if an injection vector bypasses the AST parser.

2. **CORS & Multi-Client MCP Transports:**
   * In [`apps/backend/src/api.ts`](file:///home/s5sajid/projects/learn-pos/apps/backend/src/api.ts#L18-L21), CORS is locked down to `FRONTEND_URL`. Web-based MCP inspector tools or client apps connecting from other local origins will fail preflight checks. Ensure the `/ai` route either exempts preflights for non-browser MCP clients or explicitly allows the necessary headers (`Authorization`, `Mcp-Session-Id`).

3. **Tool Design vs. Direct SQL:**
   * While an arbitrary SQL runner is useful for an internal MVP, domain-specific tools (e.g. `get_inventory_summary`, `query_sales_metrics`, `search_products`) provide stronger guarantees, more stable caching, and significantly less exposure to prompt injection compared to exposing a raw SQL endpoint to an LLM.
